# Storage ownership and scaling

Stream2Pretrain has two independent kinds of scale:

1. Compute scales with Kafka partitions, consumer replicas, and KEDA after the
   target-cluster throughput benchmark establishes safe limits.
2. Durable corpus storage scales behind the S3 API. The application does not
   require MinIO specifically, so a production deployment can use an external
   S3-compatible service or a measured distributed MinIO tenant.

Increasing a Kubernetes PVC is not the storage architecture. It is safe only
when the selected `StorageClass` is backed by expandable block storage and has
`allowVolumeExpansion: true`. The DHBW demo currently uses k3s `local-path` on
a worker's root filesystem. That provisioner neither supplies new physical
capacity nor enforces the claim's nominal size, so increasing `spec.resources`
would not add disk and a PVC autoresizer would only hide the same limitation.

## Byte ownership

| Data | Durable owner | Growth and lifecycle |
| --- | --- | --- |
| Raw admitted source bodies | `s2p-bronze` object bucket | One compressed object per retained source version. Apply the reviewed raw-data retention policy only after replay and audit requirements are agreed. |
| Structured scientific JSON and figure assets | `s2p-silver` object bucket | Retain with the source version they describe. Redpanda's `docs.normalized` topic is transport and replay state, not the long-term artifact store. |
| Licence-admission ledger | Iceberg Parquet and metadata in `s2p-gold` | Append in batches. Expire old snapshots and remove orphan metadata; keep the current table state and policy audit history. |
| Curation decisions | Iceberg Parquet and metadata in `s2p-gold` | Every accepted and rejected scored result. This is deliberate audit data and normally outgrows curated text by row count. |
| Curated training rows | Iceberg Parquet and metadata in `s2p-gold` | Accepted-only, mixture-ready corpus. Data files are the training source of truth. |
| Decontamination attestations | `s2p-decon` objects plus Redpanda events | Small signed audit artifacts. |
| Post-training tasks, trajectories, and packages | `s2p-posttrain` objects plus the foundry state database | Retain accepted artifacts and the audit record according to the post-training policy. |
| In-flight event log | Redpanda PVC | Bounded by topic retention. It is replay transport, not the only corpus copy. |
| Curator/foundry checkpoints and queues | Their application PVCs | Operational recovery state. Back up or recreate according to each component's recovery procedure. |
| Iceberg catalog pointers and authorization | Polaris persistence | Production requires a relational backend and backups. The DHBW dev in-memory catalog is not a recoverable production design. |

The raw, structured, decision, and Gold tiers can refer to the same document,
but they are not redundant copies: they preserve input evidence, extraction,
policy outcome, and trainable output respectively. The waste in the August 2026
incident was not corpus data. It was excessive Iceberg metadata generated by
per-record commits and retained orphan metadata files.

## August 2026 incident and guardrails

The single-node MinIO directory grew to 40.56 GiB. `s2p-gold` accounted for
38.61 GiB, with almost all of that in the Iceberg metadata directories for the
decision and licence-admission tables. The current metadata JSON had grown to
about 4.8 MB because fallback snapshot properties were copied into every later
table metadata document, and roughly 7,800 one-record commits were made per
table. Old unreferenced metadata remained on disk.

The repair:

- commits records or a time-bounded batch instead of committing every record;
- deduplicates licence admissions before writing;
- stores snapshot properties as snapshot metadata without accumulating them in
  table properties;
- runs an hourly Iceberg maintenance job with explicit snapshot and orphan
  safety windows;
- keeps maintenance deletion dry-run capable and refuses to delete current or
  referenced metadata;
- makes deployment fail early when object storage has no ready endpoints;
- exposes read-only storage, PVC, node-filesystem, and DiskPressure diagnostics.

After the guarded recovery, the MinIO directory measured 4.41 GiB and
`s2p-gold` measured 2.42 GiB. Those figures are an incident measurement, not a
future capacity estimate.

## Production scale plan

1. Put all five application buckets on an external S3-compatible service, or a
   distributed MinIO tenant whose data volumes are independent of k3s node root
   disks. Enable object versioning and a second failure-domain backup where the
   chosen service supports them.
2. Give Redpanda, Prometheus, curator state, and foundry state separate
   expandable CSI volumes. Do not co-locate bulk object data on those volumes.
3. Measure retained compressed bytes per admitted document, structured-asset
   bytes per document, Gold bytes per accepted document, admission rate, and
   retention horizon. Size from those measurements plus the provider's failure
   and compaction headroom; do not copy the dev claim sizes into production.
4. Alert on object-store free capacity and projected exhaustion, node
   filesystem pressure, failed Iceberg maintenance, Redpanda retention usage,
   and catalog backup age. Treat automatic expansion as a last-mile response,
   not as the only capacity plan.
5. Load-test the measured ingest rate, object-store throughput, Iceberg commit
   rate, recovery, and restore before enabling KEDA or increasing partition
   counts. Compute autoscaling must never outpace the storage write budget.

The immediate DHBW cluster can continue as a bounded lecture demo after the
metadata repair. It cannot honestly be called an automatically scalable
large-corpus store until an expandable CSI class or external object store is
available and its credentials, quota, throughput, backup, and restore path are
verified.
